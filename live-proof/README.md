# Live Proof

## What it is
This skill runs a live proof: the finished product is run on the real system it was built for, with real work, and a verdict is recorded that names anything the run did not carry. It loads at a Step 18 opening, at a Step 21 confirmation in part, for a stage 7 proof in this programme, and mid run when a defect, blocker, halt, failure, handover, interruption, takeover, abort, or environmental event lands in a proof run. It also loads for a blocked, suspended, or not opening Step 18 case, and for a bounded proceeding ruling request at a blocked gate. It does not load for a suite run, a staging or test environment check, a demo, a sequencing question, a standalone live product page check outside a proof, the release gate, the Step 19 audit, or Owner preparation work.

The procedure checks its gates in order before the run opens. Gate 0 names the proof record author, the record home, and the install record checker. Gate 1 checks the plan in hand, which names one real target and the version to prove. Gate 2 checks the target readiness position, signed by the Live-proof Owner across environment, credentials route, onboarding, and live data. Gate 3 checks the install register record as its own gate. Gate 4 reads the tier. Gate 5 lists every claimed route, and Gate 6 states the sample basis for sampled behaviour. The run then opens on the real target only, exercises each listed route at least once with real work, keeps the target stable, records environmental events separately, and preserves its logs. A run on the wrong target proves nothing about the right one.

The verdict forms are strict. PASS stands only on full coverage, with every claimed route exercised and no bound standing. Where any route, leg, behaviour, or sample did not carry its claim, the verdict is PASS-QUALIFIED and each bound is named inside the result. There is no FAIL verdict and no substitute verdict in this skill: a blocked step records SUSPENDED and claims no result while the blocker stands, and a failure is filed as a failure record. At Plaid a bounded leg is a failed proof, so no PASS-QUALIFIED verdict stands there. The confirmation form at Step 21 is narrower than the first proof: it covers fixed defects and a regression sample, not every claimed route again.

## Example
In this skill's own stage 7 proof, the runner read the skill cold from its catalogue location and ran it against a real target, the test queue tool. The gates were walked in order and recorded in the skill's own terms. Where a stage 7 counterpart did not stand, none was invented, and that absence was carried as a bound instead of being smoothed over. Through the queue, 27 of 27 tests passed on the PC bench, with the queue tool exiting 0 on all 27 jobs, in plain arrival order and with no overlap. The verdict was PASS-QUALIFIED, never an unqualified pass, with bounds B1 to B6 named in the record: B1, no plan in hand; B2, no readiness counterpart; B3, no install register counterpart; B4, tier not read, with the form not standing if the tier is Plaid; B5, working logs in scratch only; and B6, the tool's own suite not run. A later annotation added a bound for the unexercised cross project limb of one claim, which had been exercised within one project only. A confirmation proof on a second real target, the bench runner, also ended PASS-QUALIFIED, with its own bounds CB1 to CB7 named.

## How to use it
Place the folder in an agent skills library. The skill loads on its own when a request matches one of the situations above, and a person can also ask directly in plain words, for example by asking for a live proof to be run on a named build, or for a blocked Step 18 case to be recorded.

The inputs are the live proof plan, the finished product installed with its install record, the target readiness position, the routes the product claims, the sample basis for sampled behaviour, the Owner proof conditions, and the tier. The outputs are the records the case produces: the live proof record, the target readiness record, and, as the case requires, a confirmation record, a record of absence, a SUSPENDED record, a failure record, or a protection record inside the proof record. Where an input is missing, thin, or contradicted, the skill records the blocker or the bound in its own form rather than claiming a result the run did not carry.

## For agents
Follow the gates in order, Gate 0 to Gate 6, before the run opens, and follow the procedure steps in order during the run. Name the record author, the record home, and the install record checker first: a gate checked before that naming stands unchecked. Open only on the real target the plan names, exercise every listed route at least once with real work, and read the tier again before any verdict. Give PASS only on full coverage. Give PASS-QUALIFIED wherever any bound exists, name each bound inside the result, and never present a qualified verdict as an unqualified pass in a headline or a summary. At Plaid, treat a bounded leg as a failed proof. Never use this skill for a suite run, a demo, or the release gate, and never let a bundled Never item ride in as the opening act of a wider request. Where this skill and the build flow documents it rests on disagree, the documents win.
