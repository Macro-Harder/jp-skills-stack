## Inputs

A run takes seven inputs. Each input below names its supplier as the brief names it and states what stands as the input in hand. No procedure step invents a fallback for an input that is not in hand in the form stated here.

### Input 1: the live proof plan

Supplier: the build design plan.

The input in hand is a live proof plan naming the real target, the routes to be exercised, and the real work to be done. The agreed proof script sits under the plan and operationalises it. The script does not replace the plan.

Construction, labelled: an unnamed real work item is treated as a bound, because the unnamed part cannot be proved. Where the plan names a route and names no real work for it, the unnamed work stands as that bound in the result, recorded under this construction label.

### Input 2: the finished product, installed, with its install record

Supplier: the Installer, as recorded in the install register. The product itself is supplied by Step 17 closing, and at Step 21 by Step 20.

The input in hand is the finished product installed on the real target the plan names, with an install register record carrying source, version, target, and verification result on the live target. This input is a precondition of the proof running at all. It stands outside the readiness signing and is checked as its own gate, separately from readiness, at Gate 3 in Procedure.

### Input 3: the target readiness position

Supplier: the Live-proof Owner, in the Owner target readiness record.

The input in hand is a position in one of two arms only. Either readiness is signed across environment, credentials route, onboarding, and live data, each item recorded ready in that record, or a blocker is recorded in that record. Silence is not a position. A partial signing is not a position. A signing that leaves an item unaddressed is not a position.

### Input 4: the routes the product claims

Supplier: the product own claims, listed before the run.

In sequence, the product own claims supply the raw set, and the plan and then the proof script supply the listed set the proof will exercise. The proof is judged on the claimed set, not only on the listed set. The input in hand is the full set of routes the product claims, listed, each one identifiable as one route.

### Input 5: the sample basis for sampled behaviour

Supplier: the proof script agreed with the Project Manager.

The input in hand states, before the run, which behaviour is sampled rather than fully exercised, what the sample will be, and what n is planned. The claim, in the plan and in the product own material, fixes what the sample has to carry. The Owner preparation supplies the live data the sample is drawn from.

### Input 6: the Owner proof conditions

Supplier: the Owner.

The input in hand is target environment details matching the plan named target, an approved access route that has been verified and not merely named, and live data requirements that the readiness record can be checked against.

Construction, labelled: the verification of the access route covers the access the proof routes require, at the privilege those routes require, and a verification for narrower access than the proof routes require, at lower privilege than those routes require, does not satisfy this input.

Construction, labelled: the verification stands verified for the opening it serves only where the access it verified is confirmed at that opening, by the same route, as still standing, and an opening with no such confirmation treats the route as unverified under the thin or contradicted input case in Edge cases.

### Input 7: the tier

Supplier: the build record.

The tier is read before the proof opens, because the tier decides in advance which verdict forms exist. The verdict forms themselves are source rule. Below Plaid, a bound gives PASS-QUALIFIED with the bound named. At Plaid, there is no PASS-QUALIFIED live proof, a bounded leg is a failed proof, sampling inside a verdict is prohibited, and qualified closure forms are not available.

Construction, labelled: the tier is read from the design plan staffing item, R-10 item 4, at the tier recorded under R-4, the rule under which the tier is recorded in the design plan, and no verdict form is assigned until the tier is read. The consequence of a tier defect entry stands at Gate 4 in Procedure and in the record forms in Outputs. It is not restated as an input rule here.

### The one route position for inputs 3 and 6

Construction, labelled, under the Open-31 construction: the credentials route in the readiness position at input 3 and the approved access route in the Owner proof conditions at input 6 are treated as one route. The verification duty attaches to that one route. A route recorded ready that access was not verified through satisfies neither input.

### Behaviour on a bad input

This part restates no missing, thin, or contradicted input behaviour. That behaviour stands in Edge cases. A runner who meets an input that is missing, thin, or contradicted follows Edge cases for that input, and no step in Procedure supplies a different handling.

## Procedure

### Step 2: Gate 1, check the plan in hand

Check the plan in hand against the build record. The plan is the live proof plan for this build in the design plan the build record names. It names one real target. It states the version it plans to prove.

A plan that fails any part of this check, a plan naming two real targets, and a plan the build record does not name for this build are each recorded as a blocker on the R-11 pattern, naming the plan, its supplier, and the failed part. No proof result is claimed while the blocker stands. The blocker is owned and escalated in the recording and escalation form of the canonical gate passage at Step 3. That reference is to the form only.

Construction, labelled: this provenance and currency check is a construction, because the source requires the plan and states no check of this kind.

Construction, labelled: the only lift for a blocker under this gate is a plan supplied that passes this gate, in readable form, naming one real target and the version it plans to prove. No other act lifts it.

### Step 3: Gate 2, check the readiness position

Check the target readiness position supplied by the Live-proof Owner against its record form in Outputs.

Readiness stands only where the record names the target the plan names, names the Owner as its signer, and records the signing time, and where readiness is signed across its four items: environment, credentials route, onboarding, and live data, each recorded ready. A record naming no target, or a target the plan does not name, stands as no position for this run. A record with no Owner name stands unsigned, and unsigned is neither arm of the position. This skill consumes the record as a gating input and signs nothing at this gate.

Construction, labelled: a record with no signing time recorded stands unsigned for the purposes of this gate, in the same way as a record with no Owner name.

Construction, labelled: where the signing rests on access not verified through the one route named in Inputs, or on preparation the Owner own record shows as not done, the signing is checked against the preparation record and, where the two do not agree, the signing is treated as not made and the case routes as a blocker. The source requires both the preparation and the signing, and states no cross check between them.

Construction, labelled: where the target, the environment, the credentials route, or the live data has changed since the signing, shown by the readiness record or by any input of the run that records the change, the signing stands stale and is treated as not made, and the case routes as a blocker under the canonical gate passage below.

Construction, labelled: the access verification behind a signing stands verified for the opening it serves only where the access it verified is confirmed at that opening, by the same route, as still standing, and an opening with no such confirmation treats the route as unverified under the thin or contradicted input case in Edge cases.

Construction, labelled: a verification for narrower access than the proof routes require, at lower privilege than those routes require, does not satisfy input 6 and does not support a signing at this gate.
