# Experimenter Method

## What it is
This skill turns a contested, load-bearing assumption behind an idea into a falsifiable test. A contested assumption is one that is disputed, uncertain, or not agreed rather than a settled fact, and a load-bearing one is one the idea depends on, so that if it is wrong the idea fails or changes materially. For each such assumption the skill fixes four things in writing before the run: the hypothesis, the specific expected outcome in a form that can be checked against what actually happens; the metric, what is counted and how it is counted; the falsifying result, the specific outcome that would show the idea or assumption has failed; and the selector criteria, the explicit rule for which cases or examples are included in the test and which are excluded. The written test plan is recorded before the run, and afterwards the result is judged only against the terms fixed beforehand.

The skill has two entry points, chosen before the work starts by whether the run has already happened. At the design entry point all five steps run in order: list the assumptions, fix the hypothesis, metric, and falsifying result, fix the selector criteria, record the plan, then judge. At the judging entry point only the judging step runs, over a completed run offered as proof. The same gate applies there: a run testing an assumption that is not listed in the plan as contested and load-bearing must not receive a pass, and a run arranged to succeed, set up, selected, or tuned so that a successful outcome is expected rather than decided by the outcome, is named a demo, not an experiment. Edge cases are covered in the skill itself: assumptions left out of the plan, a lock that cannot be fixed, the timing of the locks, a pre-run lock revised after the run, overlapping verdict conditions, and the quality bars that apply at judging.

## Example
A team believes new users do not find the help articles, and proposes an onboarding checklist. The assumption is contested and load-bearing, so a test plan is recorded before anything runs: the hypothesis is that support tickets from checklist accounts fall at least 20 percent against control accounts in the first 30 days; the metric is the count of support tickets opened per account in its first 30 days, counted from the support queue and split by group; the falsifying result is tickets from checklist accounts equal to or higher than tickets from control accounts in the same window; the selector criteria include every new account created in a stated six day window, assigned alternately by creation order to checklist or control, excluding staff accounts and accounts that cancel within 24 hours for a billing error. Each lock is timestamped before the run. When the window closes, tickets from checklist accounts have fallen 22 percent against control. The verdict is a pass, judged only against the terms fixed before the run: the observed fall meets the 20 percent fall fixed in the hypothesis, no demo condition applies, and the gate and the quality bars pass.

## How to use it
Place the folder in an agent skills library. The skill loads when an idea rests on an assumption that is contested and load-bearing and a test is being designed, and when a completed run is offered as proof of an idea and has to be judged. A person can also ask directly in plain words, for example by asking for an experiment to be designed for a named assumption, or for a named run to be judged as a test.

The inputs are the idea and the assumptions behind it, any plan record that lists which assumptions stand as contested and load-bearing, and, at the judging entry point, the recorded test plan and the run's observed result with its arrangement facts. The output at the design entry point is the recorded test plan: the assumption, the hypothesis, the metric, the falsifying result, and the selector criteria, each lock timestamped before the run. The output at the judging entry point is a verdict judged only against those fixed terms, naming a demo where a demo condition applies. Where a lock cannot be fixed before the run, the skill's stop rules end the work at that point rather than letting the run proceed unlocked.

## For agents
Follow the five steps in order, with no branches inside a run. Choosing the entry point before the run starts is a dispatch, not a branch: the judging job starts at the judging step and does not run the design steps. Do not test only the assumptions that are easy or safe, and do not accept a presenter's word that an assumption is settled; contested is shown by disagreement or uncertainty, not by a label the presenter controls. Never move a lock after the run, never judge against terms other than the ones fixed beforehand, and never pass a run whose assumption is not listed in the plan as contested and load-bearing. Name any run arranged to succeed a demo, not an experiment. Where this skill and its source, LEVEL-2-STEPS.md Step 5, disagree, the source wins.
